# 需求、现状与实施计划

更新于 2026-11-21。首轮环境为 Arch WSL 运行 DSH Web，Windows 桌面接收通知。插件版本为 `0.3.0`（本地候选）。Windows 原生通道已成为默认交付路径；用户已在日常 profile 验证通知中心返回已有会话。本机 DSH 为 `0.2.2-rc.5`，此前的独立实例验收基于 `0.2.2-rc.1`。

## 1. Windows 通知体验

Windows 原生应用通知是唯一桌面提醒界面。横幅自然消失后，用户仍可在 Windows 通知中心找到该条目，点击回到事件所属的 DSH Web 会话。横幅和中心条目是同一条通知。Windows 控制外观、展示位置、停留时间、清除和系统级显示策略。按原生模板使用会话标题、必要摘要及操作。复杂交互使用 DSH 本身的页面。

| 事件 | 原生通知内容与动作 | 历史条目 |
|---|---|---|
| 一轮结束 | 会话标题、完成或异常原因，点击回会话。沿用完成、错误、长度限制、阻塞的区分及主动中止默认静默 | 自然消失后保留；同一会话开始下一轮时保留先前完成记录。用户可清除，留存受系统策略约束 |
| 审批 | 工具与必要理由；目标为原生「允许一次」「拒绝」，正文打开会话。缺少唯一有效关联或在线已认证所有者时只提供回会话 | 审批在任意端结束即撤下可操作条目；历史点击须再验有效性 |
| 提问 | 显示问题摘要或题数。首版建议为单条明确的文本或单选题试验原生快速回答；多题、多选、自定义组合和需完整上下文的题目点击进入原 Web 表单 | 已回答或失效即撤下可操作条目。简单题仅在原生控件能完整表达答案且一次提交通过时启用 |
| 计划审核 | 短摘要、进入对应会话阅读完整计划并按 DSH 原有选项处理 | 状态变化后撤下待审核条目 |

首轮退役 PowerShell WinForms 和 Electron 自绘窗口，移除旧浏览器作答窗的插件入口。可有无界面的 Windows 投递与激活程序。原生通道不可用时，设置页说明原因及恢复办法。Linux 原生桌面留待独立验证；CLI/TUI 和 DSH Desktop 本轮不扩展。

## 2. 触发和音效

- 默认按事件所属会话判断。任一已聚焦且可见的 DSH 主视图正在看 A，A 的事件静默；正看 B 或切到其他应用时，A 可提醒。保留事件发生后的焦点复核、多标签统一认领和去重。
- 仅对完成通知增加四档时机：始终、离开当前会话时（默认）、离开整个 DSH 窗口时、从不。「始终」仍受插件总开关、通知开关和 Windows 设置约束。「离开整个 DSH 窗口」按该实例是否存在前台 DSH 页面判断。
- 完成时机只控制视觉通道，包括是否投递通知中心条目。未达触发条件时不产生历史条目。声音沿用独立的事件、焦点、音量、静音及音效预设规则；例如选择「从不」后，离开会话仍可仅发声。
- 审批、提问、计划、完成各自保留通知开关、声音开关及音效选择。profile 继续作为设置来源。升级时继承现有配置，新增时机只取兼容默认值；验证并发修改、离线重连和重启。
- 勿扰期间，符合插件条件的通知仍交给 Windows，按用户系统设置决定横幅和通知中心展示。声音实现须实测系统音、分事件自选音及仅声音路径，避免双响；建议默认在系统勿扰时抑制插件主动播放的音效，退出后不重放。手动勿扰、自动全屏规则、单独禁用横幅、彻底禁用应用通知分别验收。
- 只观察 `session/event`，继续使用既有认证和 Pending.answer。关闭、清除、过期、重连都不代表用户同意；动作必须显式、按实例／会话／请求复核，仅交付一次。确认丢失时回会话核对。

## 4. 实现边界

复用 Host 的事件身份、认领、presence、profile 设置，以及 Web 的会话定位和一次性应答校验。替换 `src/host/delivery.js` 对桌面投递结果的处理、Windows 展示后端、安装器和对应的窗口冒烟。原生接口接受投稿、通知中心出现、横幅实际可见、用户点击、DSH 动作完成须分别记录。

优先试验 Windows App SDK 无界面辅助程序。验证当前用户安装、稳定的应用名称与标识、升级及冷启动激活；根据实测选择打包方式。为每条通知分配与实例、会话、事件对应的 tag/group，正文激活定位到可信的实例地址。延迟点击不能依赖旧渲染进程或通知中保存的登录凭据。交互动作使用可失效的引用，宿主不可达或请求已变化时只允许导航或报告失效。[微软本地应用通知概览](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/) · [通知激活](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart) · [历史条目管理](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/manage-app-notifications)

## 5. 实施顺序与验收门槛

| 阶段 | 交付 | 进入下一阶段的证据 |
|---|---|---|
| 1. 完成提醒纵向原型 | 隔离 profile 核对 rc.5 原生完成事件，WSL → Windows 原生通知 → 默认浏览器中的目标会话。验证辅助程序安装身份与退出后激活 | 前台看 B，A 完成；横幅自然消失，Win+N 中能找到 A，辅助程序已退出仍能点击到 A。分别验证网页在线、网页已关及需重新登录；阻塞点记录在对应环节 |
| 2. 统一策略与历史管理 | 接入四类事件、完成时机、独立音效、历史去重与过期处理；绑定持久的实例身份，隔离不同 profile | 同一事件只投递一次，同会话不同轮次各留一条；聚焦 A／看 B／切其他应用及多标签通过；四种通知与声音组合、勿扰和系统禁用场景通过。后台重启后点击仍定位正确 |
| 3. 原生操作与回会话 | 原生审批、简单题原型；复杂题和计划由原 Web 完成；联动旧通知撤回 | 真实允许及拒绝各执行一次，Web 抢先处理或过期后点击无法再次作答；断网不自动重试。完整批次与计划在目标页面可继续；清除通知不改变 DSH 请求 |
| 4. 替换与交付 | 正式投递只走原生通知；删除 WinForms、Electron 窗口及旧入口，更新禁用方式、诊断、安装升级／卸载、测试和构建产物 | 日常 profile 与默认浏览器验收；新装、从旧版升级、辅助程序缺失、系统关通知均无旧窗弹出，升级保留设置，卸载清理本插件注册；pnpm verify 及打包安装通过后准备发布 |

阶段 1 用隔离实例验证，避开日常会话。切换正式通道时，同一事件只启用一种展示方式。首个里程碑取决于通知中心留存和延迟点击的实机结果，不能以设置页演示、API 返回成功或旧 Electron 冒烟代替。原 P0–P5 的验收证据按日期保留在 [verification.md](verification.md)；阶段 1–4 的本机验收及剩余环境边界见[正式通道验收](verification.md#17-正式通道安装升级与卸载)。下一步为候选包发布决策。[原生动作与失效复测](verification.md#16-原生动作与失效复测)。系统限制的实际来源和日常环境边界见[阶段 2 验收记录](verification.md#15-四类原生通知与历史管理)。阶段 1 的复现、用户确认与重新登录边界见 [验收记录](verification.md#14-windows-通知中心完成提醒)。
